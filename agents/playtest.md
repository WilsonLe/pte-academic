# Playtest

Use this workflow when asked to “playtest”, run a “playtest session”, play the app as a student and suggest improvements, or run an “autopilot playtest”. Ordinary playtesting produces evidence of real learner friction and a short, prioritized improvement report. When implementation is also requested, fix the agreed problems and playtest the resulting candidate again. An explicit autopilot playtest invocation selects the [one-cycle delivery mode](#autopilot-playtest-one-cycle) below.

## Start in the app

1. Read the current [project instructions](../AGENTS.md). Reuse the user's scope, supplied route and settled preferences. Default to a beginner who knows nothing about PTE: discover what to do through the interface before inspecting implementation or answer keys.
2. Open or select the app in the **visible built-in browser** and inspect its actual state. Use browser controls and screenshots to interact with it. Source inspection and automated tests supplement this walkthrough. If the built-in browser is unavailable, report that blocker and any separate evidence; do not claim a browser playtest from code inspection.
3. Record the URL, revision/worktree, preview mode, viewport and starting learner state. Verify which checkout the server serves. For a changed candidate, use its built static preview following the [build/hosting instructions](../README.md#build-and-host). Automated checks use their own isolated ports and profiles as described in [Commands](../AGENTS.md#commands).
4. Preserve existing sessions, recordings and progress. Ordinary playtesting authorizes saving a practice attempt through normal controls. Use an isolated profile for seeded fixtures or destructive/reset cases. Keep recordings on device and follow the project's privacy and authoring boundaries; playtesting needs no paid content generation.

## Play as a beginner

Complete at least one coherent journey: choose practice, understand preflight, start, answer, finish, inspect Feedback, then reopen the saved session from History. Include a deliberate mistake or skip so feedback has something useful to explain. Record the actual question IDs/variants encountered; on retakes, exercise different variants where available. Random selection supplies variety, not proof of variant coverage; identify types with only one authored item. Do not expose hints or keys during an active attempt. Check reload recovery outside a live attempt; leaving or refreshing the runner ends it.

Explore related surfaces within scope: daily practice, question types, sections, mocks, Instructions, Learn, progress and achievements. Check how a learner returns and what state survives. A general session can sample these paths; a request covering “all” or “every” needs an inventory of affected types, response kinds, modes and shared surfaces, with a result or explicit gap for each. Use the [review audit](../docs/review-audit.md) and [UI coverage audit](../docs/ui-cleanup-coverage.md) as starting maps, then verify against the current app.

Try desktop and a narrow mobile viewport, keyboard navigation, a long prompt/response and a short window where relevant. Read every affected page, open and dismiss detail controls, and check focus returns. Verify complete text, readable controls, correct Question/Feedback counters and reachable actions. Respect contained scrolling and the measured-page rules in the project instructions. Restore temporary viewport changes at the end.

For speaking, exercise playback, preparation/error states and available review/retry controls. State whether evidence came from an actual recording/inference, a synthetic microphone or a controlled saved assessment. Fixture rendering cannot establish recognition or pronunciation quality; preserve uncertainty and the [scoring limitations](../docs/test-fidelity.md).

## Judge improvements by learner purpose

- Identify what the student is trying to do, what blocked or confused them, and why the existing screen failed. Treat missing task context as learner friction even when its text can be found through a secondary control. Distinguish observed behavior from a hypothesis or personal preference.
- Prefer removing duplication, correcting labels, regrouping controls or reusing existing components. Keep the primary task obvious. Do not add new learning content, default tips, banners or repeated explanations to solve interface friction unless specifically requested.
- Judge Feedback by reflection: the original question and response must be usable together before opening a disclosure. Read the full passage, numbered gaps/paragraphs, choices or chart as applicable, and verify their meaning survives paging and viewport changes. Passing controls, accessible names and geometric fit alone cannot establish this learner outcome.
- Put necessary supporting detail behind a clear click/selection, tooltip or existing disclosure. Keep it discoverable and keyboard accessible. Show complete detail when opened; hiding or clipping essential instructions/answers is not a clutter fix.
- Make feedback local to the response: clickable red/green differences for objective answers, with labels or other non-color cues and explanations on selection. Reorder explanations must explain why each paragraph belongs first/last and how it connects to both available neighbors. Keep writing alternatives/planning outlines neutral and speech's acoustic uncertainty intact. Apply a requested feedback pattern across every affected question type without inventing unsupported correctness or scores.

## Record findings

Keep a compact report in the session; retain larger screenshots/logs in the existing ignored `artifacts/` area. Commit curated evidence only when needed for an authorized change. Record enough surrounding screen context to show the problem, without exposing private learner material.

For each finding, capture:

- **Priority and location:** learner impact, screen/route, mode and question/type if relevant.
- **Reproduce:** starting state and the exact actions taken.
- **Observed vs expected:** what happened and what the student needed; attach evidence when useful.
- **Smallest useful improvement:** intended behavior, what stays hidden until requested, and how to verify success.

Finish with the prioritized findings, coverage/revision and any untested paths or blockers. A clean session reports what was exercised and what remains unknown. Do not present suggestions as implemented or automated checks as manual observations.

## Implement and playtest again when requested

A plain playtest ends with findings. “Implement these improvements and playtest again” authorizes the implementation loop within that scope; carry forward settled decisions without another routine confirmation. Follow the [repository change rules](../AGENTS.md#content-and-product-boundaries): issue before edits, isolated feature branch, focused checks, linked draft PR and one independent review. Read [content instructions](../content/AGENTS.md) before any authored-content edits.

Translate each accepted finding into an observable acceptance check, update the existing owner, and keep the default screen compact. Reopen the **built-in browser** on the resulting candidate and repeat the original failing actions plus affected neighboring paths. For a pattern-wide change, reconcile the inventory rather than stopping at the first working question. Compare before/after results and report remaining issues. Run focused regression checks for the changed behavior; the full repository suite belongs to an authorized merge stage.

Reconfirm the served revision before retesting. A cached PWA can keep showing an older shell even after rebuilding or stopping a server. Check server identity and the app's update state before classifying a regression; use the explicit update/reload flow outside an active attempt. Preserve learner/model storage. If setup, model preparation or browser access blocks progress, record the failing step and last verified state, continue independent checks, and resume from that checkpoint after recovery.

End with findings resolved/open, exact candidate and evidence, validation limits and any draft PR links. Leave a useful app view open. Merge and deployment need their own authority for the named change; approval for an earlier playtest's PRs does not authorize later ones.

## Autopilot playtest: one cycle

Trigger this mode only when the user explicitly asks to **run an autopilot playtest** (or explicitly requests the equivalent playtest → implement → auto merge → verify cycle). Asking to introduce or edit this workflow does not run it. A plain playtest or request to implement findings keeps the ordinary behavior above.

The invocation authorizes choosing and fixing observed, in-scope learner friction and merging the resulting cycle branch through its linked PR into `main`, including later in-scope review/test fixes. Record the user's request, repository, base, branch and PR in the tracking issue as they become known. This is explicit authority for one ordinary delivery, not activation of a generic SDLC autopilot, orchestration control plane, recurring task or permission to merge other PRs. Do not repeat routine approval questions for this settled scope. Material scope expansion or a different merge target needs a new user decision.

### Discovery gate

Each completed autopilot cycle must reveal at least one **new, reproducible, actionable learner-friction finding** within the authorized scope, then deliver its fix through the steps below. A passing walkthrough, repeated known issue or list of exercised controls does not satisfy this gate. A regression of a previously fixed issue can qualify with fresh evidence on the current revision. Never invent a defect, inflate impact or make a cosmetic change solely to fill a cycle.

- Before each cycle, read prior findings and coverage. Choose an unanswered question about a learner goal, prioritizing underexplored or risky states rather than repeating an easy passing path.
- Complete the coherent beginner journey first. If it reveals no qualifying finding, perform three additional materially different probes within the same cycle, stopping early when a finding is substantiated. For each probe, record the hypothesis, starting state, expected learner outcome and observed evidence. Useful probes include discovering an explanation without prior knowledge, recovering from an allowed failure, retaining state after reload, or reading long content with keyboard/short-window constraints. Respect the user's scope, privacy and setup boundaries; do not inspect keys during an active attempt.
- Before selecting a fix, record the learner goal, reproducible friction, evidence, why it is new relative to prior findings, and an observable acceptance check. Favor the highest learner impact supported by that evidence, then choose the smallest useful fix.
- If all three extra probes are clean, report **discovery exhausted**, the explored hypotheses, remaining unknowns and the next useful scope. If a prerequisite or scope boundary prevents the probes or an in-scope fix, report that concrete blocker. In either case, leave the cycle incomplete and uncounted, stop any requested batch with its remainder pending, and retain evidence for resuming the same cycle. Do not search indefinitely or create an empty PR.

For an explicitly requested batch, count only cycles that satisfy this discovery gate and complete delivery and merged verification. Candidate retests and verification of an existing fix belong to its original cycle; they do not count as fresh discoveries or extra cycles.

### Delivery

1. **Playtest and discover.** Follow Start in the app, Play as a beginner, Judge improvements and Record findings above, then satisfy the [discovery gate](#discovery-gate). Use the visible built-in browser, record revision/state/coverage/evidence, and sample desktop and mobile within the user's scope. A cycle need not finish a full mock or exhaust every question unless requested.
2. **Choose a bounded fix set.** Select the smallest useful improvements supported by the new finding, with acceptance checks and explicit exclusions. Favor clearer controls and less clutter. Record the finding evidence and plan/design in a live tracking issue before implementation and use an isolated feature branch/worktree under the installed Standard Development Workflow. Preserve unrelated work.
3. **Implement and retest.** Follow Implement and playtest again above, including focused regression checks and the same failing actions in the built-in browser on the built candidate. Keep issue/PR evidence current. Playtesting does not authorize paid authoring, storage resets, model changes, new learning content or unrelated refactors; retain the project privacy and content boundaries.
4. **Open and review the PR.** Commit/push the checked candidate and open a linked draft PR. Read back every issue–PR link in both directions. Run one independent review-and-address cycle under Standard Development Workflow and Engineering Review, bound to the exact base/head. Include the discovery evidence and learner impact in the review brief so review checks that the finding qualifies as well as whether the patch fixes it. Address in-scope findings and validate the resulting head; label a pre-fix review separately. Do not substitute self-review or treat pending/failed review as complete. Follow the installed workflow's exact-candidate review gate and bounded review policy; do not start repeated reviews to exhaust findings.
5. **Pass merge gates and merge.** Run the full repository-required suite and local CI on the current candidate, using the current [commands](../AGENTS.md#commands), [verification guidance](../README.md#verify), package scripts and CI configuration as the inventory. Include root/subpath builds, local contracts and browser coverage; resolve prerequisites rather than silently skipping a required check. Fix in-scope failures, push and rerun affected checks plus the full suite. Recheck the current head/base, independent review evidence, unresolved feedback, required hosted checks, branch protection, mergeability and deployment readiness. Base/head drift invalidates affected evidence. Recheck the existing [Pages workflow](../README.md#build-and-host) before merging: `main` currently triggers publication to `https://wilsonle.github.io/pte-academic/`. Account for that automatic side effect under the installed deployment-readiness rules; if it lacks required authority or readiness, stop before merge. Do not change deployment settings or initiate a separate manual deployment. Mark the draft ready and squash-merge only this cycle's PR after these gates pass; never bypass protections or force a merge.
6. **Verify the merged revision.** Read back the PR's merged state and merge commit, then fast-forward the clean canonical `main` without disturbing other work. Build that revision and serve its static output on an isolated port. In the visible built-in browser, confirm the served revision and PWA update state, repeat the fixed learner journey and affected neighboring paths, then reopen the saved session and reload outside an active attempt. Preserve learner/model storage. A passing branch preview alone does not complete this step. If Pages runs, read back its exact deployed revision/status and smoke-test the published flow; distinguish local merged verification from live verification, and report failure, pending publication or unavailable evidence honestly.
7. **Finish and stop.** Lead with what the cycle newly revealed and the verified learner improvement. Report selected findings resolved/open, issue/PR links, reviewed and final heads, merge commit, focused/full-suite results, merged browser coverage and Pages status. Close the tracking issue only when its complete acceptance criteria are verified. Clean up only task-owned resources under the delivery workflow and leave a useful app view open. Stop after the requested cycle count; new suggestions alone do not authorize another cycle.

If browser access, setup, permissions, model preparation, review, tests, protection, deployment readiness or verification blocks a phase, retain the issue, branch/PR, evidence and last verified revision. Report the failing gate and next required action; continue only independent safe checks. Never weaken a gate or claim completion to reach the one-cycle limit. Resume the same cycle from its first incomplete phase after recovery, revalidating stale evidence rather than creating another cycle or duplicating issues/PRs. A post-merge verification failure remains an incomplete cycle with the merged revision recorded; report/track the regression without automatically merging another PR or reverting production.
